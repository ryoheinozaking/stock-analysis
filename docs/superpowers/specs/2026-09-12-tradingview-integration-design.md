# TradingView 統合 設計

作成日: 2026-09-12

## 背景

TradingView の有料プランを契約しているが、現状は日足チャートを目視で見るだけで活用しきれていない。
Claude と TradingView を接続する MCP サーバーが話題になっており（X の紹介投稿が発端）、
これを機に「トレードにもっと活用する」方法を設計する。

当初は紹介記事に従って `tradesdontlie/tradingview-mcp` を導入する方向で進めたが、
検証の結果いくつか前提が覆ったため、設計をやり直した。本書はその検証結果と方針を記録する。

## 検証で確定した事実

調べ直すコストが高いため、根拠とともに残す。

### TradingView 利用規約は自動収集を明示的に禁止している

利用規約は「スクリプト、API、スクリーンスクレイピング、データマイニング、ロボット等による
自動的なデータ収集を、**その目的を問わず**厳格に禁止する」と定めている。
市場データは「表示のみ」の用途に限ってライセンスされ、表示以外の利用は禁止。
[How bans work](https://www.tradingview.com/support/solutions/43000591357-how-bans-work/) には
この制限に違反した場合アカウントを BAN すると明記されている。

MCP サーバーが行っているのは、まさにこの禁止対象に該当する。
CDP 経由でのデータ取得に加え、ログイン Cookie を使って内部 API
（`pricealerts.tradingview.com`、`pine-facade.tradingview.com`、`symbols_list`）を直接呼んでいる。

一方で、実際に MCP 利用で BAN された報告は確認できなかった。
スター 6,000 規模のツールが約半年運用されて大量 BAN 事件が起きていない状態。
ただしツール作者自身が「アカウント BAN について責任を負わない」と免責している。

**方針**: 利用者のアカウントに関する自己責任の判断として、フル活用する。
ただし失うものを最小化するため、レイアウト設定とウォッチリストの事前退避を A-0 に含める
（Pine ソースを対象外とした理由は A-0 の節に記す）。

### Advanced Charts は個人利用では使えない

TradingView 公式の無料チャートライブラリ [Advanced Charts](https://www.tradingview.com/advanced-charts/) は、
当初「自前サーバーにホストして J-Quants データを流せば規約違反ゼロで使える」と判断したが、これは誤りだった。

ライセンス条件は「**法人**が**公開**のウェブプロジェクトやアプリで使う場合にのみ提供」であり、
「**個人利用・趣味・学習・テスト目的では提供しない**」と明記されている。
stock_analysis は個人の投資判断用ツールのため条件を満たさない。

**代替**: [Lightweight Charts](https://github.com/tradingview/lightweight-charts) は Apache 2.0 の
オープンソースで、個人利用・商用ともに制限がない。Streamlit 用ラッパーも存在し、
特に `streamlit-lightweight-charts-v5` はマルチペイン（価格＋MACD＋RSI の縦積み）に対応する。
系統 B はこちらで実現する。

ただし Apache 2.0 に加えて **帰属表示が必須**。利用者が見えるページに NOTICE ファイル由来の
帰属表示と `https://www.tradingview.com/` へのリンクを掲載する必要がある。
`attributionLogo` チャートオプションでチャート内に表示するのが推奨手段。
これは B-1 の実装要件に含める。

### 日本株は約 20 分遅延、ただし本件では問題にならない

リアルタイムデータ購読なしでは東証銘柄は約 20 分遅延する（リアルタイムは月額約 3 ドルの別購読）。
現状は未契約と見られる。

ただし stock_analysis の戦略はバリュー株 250 日保有・成長株 60 日保有が前提であり、
リアルタイム性は元々必要ない。**逆に言えば、MCP でリアルタイム監視する価値も低い**。
MCP の価値は日足ベースの「チャート判断の壁打ち」と「候補の一括確認」に集中する。

売買タイミングの通知は、日次で足りるため stock_analysis 側で実装する方が筋が通る（将来課題）。

### MCP README が定める禁止事項

README の Disclaimer 節（380-384 行）は、このツールを以下に使ってはならないと明記している。

- TradingView の市場データの再配布・転売・商業利用
- TradingView のアクセス制御や購読制限の回避
- **抽出データを用いた自動売買、またはアルゴリズムによる意思決定**
- **Pine Script インジケーター作者の知的財産権の侵害**

後者 2 つは本設計に直接影響する。

1 つ目は A-1（深層分析レポートへの統合）の位置づけに関わる。「完全自動売買」なら明確に該当し、
「人間が最終判断するレポートの材料」ならグレー。A-1 は LLM が投資判断を出力する設計のため、
**限りなくグレーに近い**。利用者の判断としてA-1まで進めるが、この位置づけは記録しておく。

2 つ目はバックアップ設計に影響した。詳細は A-0 の節に記す。

コードの静的検査結果は問題なし。

- 外部通信先は `*.tradingview.com` とローカル CDP のみ。第三者サーバーへの送信なし

将来のコードが自動で入る経路になるため、リポジトリが乗っ取られた場合の影響範囲が広い。

### 環境: TradingView は MSIX パッケージとして導入済み

Windows 版 TradingView は MSIX 形式（`TradingView.Desktop_n534cwy3pjxzj`）でインストールされている。
`C:\Program Files\WindowsApps\` 配下は権限制限があり、CDP のデバッグポート起動が
"Access is denied" で失敗する既知の問題がある。

リポジトリ側は `tv_launch` ツールで MSIX を自動検出し、失敗時は
`%LOCALAPPDATA%\tradingview-mcp\` へローカルコピー（約 330MB）してそこから起動するフォールバックを実装済み。
ただし環境によっては追加対応が必要との報告もあり、**動作保証はない**。これが A-0 で潰すべき最大の不確実性。

### MCP 設定の書き込み先

`~/.claude/.mcp.json` に書いても読み込まれなかった。
実際に効いているのは `~/.claude.json` のトップレベル `mcpServers` フィールド。
`claude mcp add -s user` で登録するのが正しい。

なお EDINET DB は `claude mcp list` に現れず、デスクトップアプリ独自のコネクタ管理で
登録されているため別系統である。

## スコープ分解

要望は 5 つ挙がったが、技術的に独立した 2 系統に分かれる。

### 系統 A: MCP 活用（規約リスクあり・Claude Code ワークフロー）

- **A-0**: 技術検証＋設定退避
- **A-1**: 深層分析への統合
- **A-2**: 候補絞り込み（Top-N 一括巡回）
- **A-3**: エントリー／保有監視の壁打ち

A-0 は A-1 以降の前提。ここが動かなければ系統 A は成立しない。

### 系統 B: Streamlit チャート刷新（規約クリーン・stock_analysis のコード）

- **B-1**: Lightweight Charts で `components/chart.py`（333 行・Plotly）を刷新

系統 A とは依存関係がなく、独立して進められる。
なお Plotly は `4_portfolio.py` / `7_pipeline_report.py` / `8_backtest_value.py` でも使われているが、
そちらは対象外とする。

**「描画層のみ差し替え」という当初の見積もりは誤り**。`chart.py` を読むと以下が密結合している。

- 一目均衡表の雲は `fill="tonexty"` で `span1.where(bull)` と `span2.where(bull)` を交互に描いて
  間を塗り分ける Plotly 固有の実装。Lightweight Charts に同等機能はなく自前実装が要る
- 価格帯別出来高は `make_subplots` の 2 列目に横向きヒストグラムとして描いており、
  Lightweight Charts の標準機能にない
- 出来高は `secondary_y` でローソク足に重ねている
- `_detect_signals` によるゴールデンクロス／デッドクロス／MACD クロス／RSI 反転の検出結果を
  チャート上に注記として描いている

したがって B-1 は以下の順で進める。

1. **計算層と描画層を分離する** — 指標計算とチャート用データ整形を、描画ライブラリに依存しない形に切り出す
2. **同値テストを作る** — 同じ入力に対し既存 Plotly 版と新実装が同じ値を返すことを検証する
3. 描画アダプタを実装する

さらに前提として、長期データで `AdjC` を直接使うと株式分割でスケールが壊れるため、
`services/split_adjust.normalize_close` を基準に統一しておく必要がある
（プロジェクトの `CLAUDE.md` に記載の既知の罠）。

A-0 → A-1 → （B-1 / A-2 / A-3 は後日判断）

## A-0 設計: 技術検証＋設定退避

### 目的

1. MSIX 環境で MCP が実際に動くか
2. 実チャートから何が取れるか（Supertrend、SQZMOM 等のインジケーター値が読めるか）
3. 同梱 `tv` CLI の能力範囲
4. レイアウト設定とウォッチリストの退避

3 が **A-1 の設計を左右する**。MCP ツールは Claude Code 経由でしか呼べないが、
CLI なら Python から `subprocess` で呼べるため、既存の `scripts/deep_analysis_helper.py` と
同じパターンに乗せられる可能性がある。

### バックアップ対象（Pine ソースは取得しない）

当初は保存済み Pine を全て吸い出して git 管理する設計だったが、以下の理由で取りやめた。

- 利用者が保有する Pine は組み込みまたは第三者の公開スクリプト（`SQZMOM_LB` は LazyBear 作）であり、
  自作のものはない。よって退避する必要がない
- `stock-analysis` リポジトリは **public**（Streamlit Cloud 無料枠の要件）。
  第三者製 Pine を置けば公開の場での再配布に当たり、README の禁止事項
  「Pine Script 作者の知的財産権の侵害」に該当する

退避対象はレイアウト設定とウォッチリストのみ。いずれも利用者自身のデータで権利上の問題はないが、
保有・監視銘柄が推測できるため git には上げない。
既存の `data/` 配下は `.gitignore` で全て除外済み（`data/watchlist.json` も管理外）であり、
同じ方針に揃える。

### サプライチェーン対策

`src/core/update.js` の自己更新機構（`git pull` + `npm ci`）は使わない。

- 検証済みコミット SHA を固定する（本設計時点の HEAD: `c05b8f5`）
- 更新が必要な場合は差分をレビューしてから手動で実施
- `tv_update` ツールは呼ばない

### CDP の運用ルール

- 起動後に `127.0.0.1` バインドであることを確認する（外部公開されていないこと）
- 使い終わったらポート 9222 を閉じる。常時開けたままにしない
- 作業単位で起動・終了する

### 手順

1. `claude mcp add -s user tradingview -- node C:/Users/ryohei/tradingview-mcp/src/server.js`
2. Claude Code 再起動
3. `tv_health_check` で接続確認
4. 失敗時は `tv_launch` で MSIX フォールバックの動作を確認
5. `chart_get_state` / `data_get_study_values` で 5016 の実データ取得
6. ウォッチリスト取得・レイアウト情報取得
7. `tv` CLI の能力確認（非対話での JSON 出力が可能か）
8. CDP を閉じ、TradingView が通常起動に戻ることを確認

### 成功条件・撤退条件

「5016 で指標値が一度取れた」だけでは不足。以下を判定表で確認する。

| # | 判定項目 | 成功基準 |
|---|---|---|
| 1 | MSIX 環境での起動 | `tv_health_check` が `cdp_connected: true` を返す |
| 2 | CDP バインド | `127.0.0.1` のみ。外部インターフェースで待ち受けていない |
| 3 | 指標値の取得 | Supertrend / SQZMOM の現在値が数値として読める |
| 4 | Pine 描画の取得 | `data_get_pine_lines` / `labels` が意味のある値を返す |
| 5 | CLI の非対話出力 | `tv` コマンドがパイプ可能な JSON を返す |
| 6 | 起動済み TradingView の復旧 | `taskkill` 後、ログイン状態・レイアウトが保持される |
| 7 | CDP 終了後の復旧 | ポートを閉じた後、通常起動で問題なく使える |
| 8 | 再現性 | 固定 SHA `c05b8f5` で 1〜7 が再現する |

**撤退条件**: 1 または 6 が満たせない場合、系統 A を見送り B-1 へ切り替える。
6 が満たせないということは、検証のたびにチャート環境が壊れることを意味し、
継続利用に耐えない。

3 と 4 が満たせない場合、A-1 の価値（利用者固有のチャート環境を読む）が消えるため、
A-1 は中止し A-0 で得た知見のみ記録する。

### リスク

- `tv_launch` は TradingView を `taskkill` で強制終了してから起動し直す。開いている画面が一度閉じる
- MSIX フォールバックが走ると約 330MB のローカルコピーが作られる
- CDP ポート 9222 が開いている間、ローカルの任意プロセスから TradingView を操作可能になる
- TradingView のアップデートで内部 API が変わり、動作しなくなる可能性がある（README も警告）

### J-Quants との突き合わせ

TradingView の 2026-09-09 のバーの終値 3,909 が、J-Quants の同日終値 3,909.0 と**完全一致**。
分割調整のスケールずれもない。

一方で **J-Quants の `prices.parquet` は 2026-09-09 で止まっており、TradingView の方が
2 営業日新しかった**（2026-09-11 まで保持）。parquet は手動更新のため、
鮮度では TradingView が勝つ場面がある。

### 取得できなかったもの・制約

1. **Pine 描画系 4 ツールは全て空**（`study_count: 0`）。
   画面の Buy / Sell ラベルは Supertrend の `plotshape()` 由来で、`label.new()` ではないため。
   ツールの不具合ではなく、利用者のインジケーター構成がこの API を使っていないことによる

2. **`data_get_study_values` の `inputs` に巨大な暗号化ブロブが混入する**。
   1 回の呼び出しで大量のトークンを消費した。A-1 では `values` のみを抽出する前処理が必須

3. **SQZMOM の値が一部欠落**。画面表示は `−91.0` と `0.0` の 2 値だが、ツールは `0.0` のみ返す

4. **`watchlist_get` が動作しない**（`Watchlist button not found`）。MCP・CLI とも同じ。
   パネルは開いている（`was_open: true`）のに失敗するため、TradingView 3.4.1 または
   日本語 UI に実装が追随していないと判断。`alert_list` / `layout_list` が `internal_api` 経由で
   成功するのに対し、`watchlist_get` だけが DOM 探索実装であることが原因と見られる。
   退避は手動で行う（ウォッチリストを開く → アドバンスドビュー → リストを TXT でダウンロード）。
   手動エクスポートは成功し、「00_ポジション」8 銘柄を `data/tradingview/backup/` に退避済み。
   なお **A-2 でウォッチリストへの書き込み（`watchlist_add_bulk`）を使う構想があるが、
   読み取りが DOM 依存で失敗している以上、書き込みも同じ実装なら動かない可能性が高い**。
   A-2 着手時に最初に検証すべき項目

5. **`tv_health_check` の更新チェックが誤った SHA を返す**。

### A-1 に残る規約上の論点

MCP の README は「抽出データを用いたアルゴリズムによる意思決定」を禁止事項として挙げている。
A-1 は LLM が投資判断レポートを生成する設計のため、この条項に対してグレーな位置にある。
最終判断は人間が下すという解釈は可能だが、断定はできない。

利用者の判断として A-1 まで進めるが、以下を前提とする。

- 完全自動の売買判断や発注には接続しない
- 出力はあくまで人間が読むレポートであり、そのまま執行に流さない
- TradingView 側の仕様変更や規約運用の変化があれば、A-1 を停止して再評価する

なお外部レビュー（ChatGPT-5）では「着手順を B-1 → A-0 → A-1 に変え、A-1 は規約判断後に再審査すべき」
との提案があった。検討の結果、A-0 の判定表で撤退条件を明確にしたこと、および
A-1 を上記の前提付きとすることで、当初の A-0 → A-1 の順を維持する。

実装形態は A-0 の結果次第で以下から選ぶ。
